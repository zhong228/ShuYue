# 紅樓夢斷行基線重錄（2026-10-01）

狀態：已重錄。`redchamber.tsv` 換成在 main（`1bcf407f`，YueduCoreText 0.6.1）上、程序語言固定為繁體中文錄的結果。9/23 的舊檔留在 `redchamber-2026-09-23.tsv` 備查。

## 起因

`BrowserLayoutLineBreakBaselineTests` 比對的基線是 9/23 在 `14c7a441`（YueduCoreText 0.6.0）錄的。10/1 在任何環境下都過不了：繁體中文 61 章不同，英文 196 章，簡體中文 246 章。fidelity loop 的斷行、行內排版切片會跑這個測試，所以這些切片會被擋住（STATE.md D3）。

## 查證：不是程式改動造成的

用暫時的 worktree 把 `14c7a441` 原樣重建。它的套件解析成和當時一樣的已發佈版 YueduCoreText 0.6.0，然後和 main 在同一台模擬器上各錄一次：

| 程序語言 | `14c7a441` 與 main | 和 9/23 基線不同的章數 |
|---|---|---|
| zh-Hant TW | 逐位元組相同 | 61 |
| en US | 逐位元組相同 | 196 |

main 另外量過 zh-Hant HK（61）、zh-Hans CN（246）、zh-Hans TW（246）。

結論：9/23 之後沒有任何程式改動改變斷行。9/23 的基線用今天任何一種語言都重現不出來，原因在程式碼以外。

是哪個環境因素，沒有再追。9/23 錄製用的那台模擬器已經刪掉，它的系統語言、地區、裝過的字型和機型都查不到了。目前只裝了一個 runtime（iOS 27.0，24A434），它的掛載目錄日期是 9/3，所以 9/23 很可能也是用它，但沒有證據。

## 程序語言會改變斷行

同一個 build 在英文下，有 196 / 458 章和新基線不同。語言固定成繁體中文後，系統語言是英文的 iPhone 18 Pro Max 和系統語言是繁體中文的 iPhone 18 Pro 錄出來逐位元組相同。後者不固定語言時也一樣。

## 改了什麼

- `redchamber.tsv`：在 main 上用 `-testLanguage zh-Hant -testRegion TW` 重錄，檔頭記下錄製時的語言。
- `BrowserLayoutLineBreakBaselineTests`：程序語言不是 zh-Hant 就直接失敗，訊息會說要加哪些參數（0.01 秒）。這樣環境不對時不會再被誤讀成斷行回歸。
- `redchamber-2026-09-23.tsv`：舊基線，原樣保留。

重錄後的驗證：iPhone 18 Pro 固定繁中跑比對，通過（187.6 秒）；iPhone 18 Pro Max 不固定語言，立刻失敗並給出上面的訊息。

## 怎麼跑

```bash
bash scripts/xctest.sh -t 1500 -- -only-testing:'yuedu appTests/BrowserLayoutLineBreakBaselineTests' -testLanguage zh-Hant -testRegion TW
```

重錄（整本約 3 分鐘）。環境變數要加 `TEST_RUNNER_` 前綴，xcodebuild 才會傳進測試程序：

```bash
TEST_RUNNER_YUEDU_LINEBREAK_REGEN=1 bash scripts/xctest.sh -t 1500 -- -only-testing:'yuedu appTests/BrowserLayoutLineBreakBaselineTests' -testLanguage zh-Hant -testRegion TW
```

重錄會直接覆寫原始碼樹裡的 `redchamber.tsv`。在別的 worktree 重錄做實驗之後，那個 worktree 的檔案就不再是基線了。10/1 的調查裡就有一次比對的是被英文重錄蓋掉的檔案，多看到一次假的 196 章。
